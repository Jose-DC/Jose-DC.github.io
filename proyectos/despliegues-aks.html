Caso laboral anonimizado

Despliegues controlados en AKS con Azure DevOps

Reemplacé scripts que se ejecutaban a mano por un kit de pipelines de Azure DevOps y scripts PowerShell para operar una aplicación multi-tienda en AKS: crear tiendas, publicar imágenes, actualizar una o varias tiendas y recuperar versiones anteriores. Los pipelines se lanzan a mano y pasan por aprobación antes de tocar producción. Aparte, en el ambiente de desarrollo, un workflow de GitHub Actions lanza el pipeline de develop con cada push.

Volver a proyectos

Situación

Problema

Cada tienda corre como una instancia propia en AKS, desplegada con Helm. Crear tiendas, cambiar su versión o volver atrás se hacía con scripts ejecutados a mano, uno por uno, con riesgo de equivocarse de destino o de versión y sin registro claro de qué se aplicó.

Decisión

Solución

Seis pipelines con formularios cerrados, simulación por defecto y un plan que se revalida antes de aplicar. Las actualizaciones y los rollback pasan por un Environment con aprobación y bloqueo exclusivo, y cada corrida guarda su plan y su resultado.

Uso actual

Resultado

Los pipelines se usan hoy en producción real, siempre lanzados a mano, para pasos a producción, tiendas nuevas y actualización de imágenes. Solo en develop el despliegue es automático: cada push actualiza cuatro tiendas de prueba.

Mi rol

Qué hice yo

  • Diseño: definí qué operaciones necesitaba el equipo, separé publicar imágenes de actualizar tiendas y decidí qué controles exigir en producción.
  • Pipelines y scripts: escribí los pipelines YAML de Azure DevOps y los scripts PowerShell que validan, planifican y aplican cada operación.
  • Develop: además, creé un workflow de GitHub Actions que lanza el pipeline de develop con cada push; producción no tiene disparo automático.

  • Operación: uso los pipelines en producción y corrijo lo que aparece al operar.

Qué incluye

Seis pipelines de operación

  • Catálogo: consulta AKS y ACR y actualiza las listas de tiendas y versiones de los formularios, para elegir solo destinos que existen.
  • Publicar imagen: construye la imagen y la publica en ACR; publicar no actualiza ninguna tienda.
  • Actualizar una tienda: cambia la versión de una tienda, con simulación previa opcional.
  • Actualizar por lote: lleva varias tiendas a una misma versión, con concurrencia configurable.
  • Rollback: recupera la imagen anterior de una o varias tiendas, en serie y deteniéndose al primer fallo.
  • Crear tienda: da de alta una tienda nueva a partir de una versión aprobada.

Procedimiento

Cómo se opera un cambio en producción

  • 1. Publicar imagen si hace falta una versión nueva; esto todavía no cambia ninguna tienda.
  • 2. Actualizar el catálogo para que los formularios muestren las tiendas y versiones vigentes.
  • 3. Simular: elegir tiendas y versión aprobada, y revisar imágenes, alcance y plan.
  • 4. Aplicar: una corrida nueva aprueba, genera y revalida su propio plan con el estado actual, y aplica.
  • 5. Validar acceso, aplicación e integraciones antes de ampliar el lote a más tiendas.

01

Producción

Formularios cerrados y simulación por defecto

Los parámetros son listas cerradas que mantiene el pipeline de catálogo. Quien ejecuta elige tiendas y una versión aprobada; si no cambia nada, el pipeline solo simula.

trigger: none
parameters:
- name: operation
  type: string
  default: simular
  values: [simular, aplicar]
- name: stores
  type: object        # lista que actualiza el pipeline de catálogo
- name: imageTag
  type: string
  values: ['<VERSION_APROBADA>']
02

Control

Aprobación, bloqueo y plan revalidado

La etapa usa un Environment con aprobación y bloqueo exclusivo, así dos operaciones no tocan el clúster a la vez. Antes de aplicar se genera un plan nuevo con el estado real, porque el clúster puede haber cambiado desde la última simulación.

- stage: Update
  jobs:
  - deployment: Apply
    environment: <ENTORNO_CON_APROBACION_Y_BLOQUEO>
    strategy:
      runOnce:
        deploy:
          steps:
          - pwsh: ./scripts/Invoke-Update.ps1 -Operation planificar
          - pwsh: ./scripts/Invoke-Update.ps1 -Operation aplicar
03

Alta de tiendas

Validar todo antes de crear

Antes de instalar, el pipeline renderiza la tienda localmente y la valida con un dry-run de Kubernetes, sin crear nada. Rechaza nombres reservados, releases o recursos que ya existen y hosts ocupados; comprueba permisos, almacenamiento, certificado y nodos compatibles. La instalación usa Helm en modo atómico y al final verifica imagen y disponibilidad.

helm template <TIENDA> ./chart -f values.yaml -f values-entorno.yaml \
  | kubectl create --dry-run=client -o json -f -

helm install <TIENDA> ./chart -n <NAMESPACE> \
  -f values.yaml -f values-entorno.yaml --atomic --wait

Seguridad y trazabilidad

Acceso mínimo y resultado guardado

Construir imágenes y operar el clúster usan identidades distintas. El acceso al clúster es un kubeconfig temporal sin permisos de administrador que se elimina al terminar, incluso si el pipeline falla. Cada corrida guarda su plan y su resultado como artefacto.

  condition: always()

- task: PublishPipelineArtifact@1
  condition: always()
  inputs:
    targetPath: resultados
    artifact: resultado-$(Build.BuildId)
05

Solo develop

En desarrollo, un push dispara el pipeline

El workflow llama a la API de Azure DevOps con el commit exacto, espera a que la corrida termine y falla si el pipeline falla. El pipeline comprueba que el código descargado coincida con ese commit. El token se guarda como secreto y no aparece en el log; una ejecución manual simula por defecto y el grupo de concurrencia evita dos despliegues a la vez.

on:
  push:
    branches: [develop]
  workflow_dispatch:
    inputs:
      operation: { type: choice, options: [simular, aplicar], default: simular }

concurrency:
  group: develop-deploy
  cancel-in-progress: false

jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - name: Lanzar pipeline y esperar resultado
        env:
          AZDO_TOKEN: ${{ secrets.AZDO_TOKEN }}
          SOURCE_COMMIT: ${{ github.sha }}
        run: |
          # POST a la API de runs con el commit, luego consultar
          # el estado cada 30 s hasta completed; salir con error
          # si el resultado no es succeeded.

Troubleshooting

Problemas reales y cómo los resolví

  • El rollback se detenía antes de tiempo: cuando varias revisiones seguidas tenían la misma imagen, el rollback no encontraba la versión anterior. Ahora busca la primera revisión exitosa con una imagen distinta. Agregué una prueba de regresión que fallaba antes del cambio y pasa después.
  • Deriva entre Kubernetes y Helm: un rollback cambia la imagen directamente, así que el Deployment y el historial de Helm quedan distintos. Un segundo rollback podía avanzar en vez de retroceder. Ahora el pipeline bloquea otra recuperación hasta reconciliar ambos estados.
  • Una alta falló antes de crear nada: el dry-run de kubectl devolvía un objeto por recurso y el script esperaba un único JSON. Cambié el análisis para procesar cada recurso por separado, sin imprimir manifiestos. Como la validación es previa a la instalación, el fallo no dejó recursos a medias.
  • Falso éxito en rollback: si la imagen destino ya era la activa, el pipeline mostraba un rollback exitoso sin haber cambiado nada. Ahora falla antes de tocar Kubernetes.
  • Timeouts ambiguos de Helm: un mensaje de timeout genérico no distingue si falló una actualización o un rollback. El pipeline resuelve el destino revisando el historial de revisiones exitosas en vez de suponerlo.

Alcance y límites

Qué muestra este caso

  • Pruebas del kit, no de la aplicación: las suites prueban los scripts del kit con Azure y AKS simulados; los pipelines no ejecutan pruebas de la aplicación ni escaneos de seguridad.
  • Producción manual: en producción el lanzamiento es manual y con aprobación; el disparo automático existe solo en develop.
  • El bloqueo no cubre todo: coordina las operaciones que pasan por el Environment, pero no protege frente a comandos ejecutados directamente en consola.
  • Rollback solo de imagen: recupera la imagen anterior, pero no revierte datos ni base de datos, y un alta fallida no se deshace con rollback.
  • Validación funcional aparte: un rollout terminado confirma el estado en Kubernetes; la aplicación y sus integraciones se validan antes de ampliar un lote.
  • Versión pública: caso anonimizado. No se publica código, nombres, repositorios, recursos ni logs internos, porque pertenecen a la empresa.

Aprendizajes

Lo que me dejó este proyecto

  • Publicar una imagen y actualizar tiendas tienen que ser pasos separados, para decidir cuándo y dónde se aplica cada versión.
  • Un formulario con listas cerradas evita más errores que una buena documentación sobre qué escribir.
  • El plan debe generarse justo antes de aplicar: una simulación de hace una hora ya no describe el clúster actual.
  • Un rollback por imagen es rápido, pero deja deriva con Helm; hay que conocerla y controlarla.
  • Las pruebas de regresión de los scripts de operación valen tanto como las de la aplicación.
  • No todos los ambientes necesitan el mismo control: develop gana con la automatización y producción con la aprobación.
