Caso de mi trabajo actual, anonimizado

Despliegues en AKS con Azure DevOps

En mi trabajo operamos una aplicación que corre como una instancia por cliente en AKS. Antes, cada cambio se hacía corriendo scripts a mano. Armé pipelines en Azure DevOps para hacer esos cambios en producción de forma ordenada, con revisión y aprobación antes de tocar el clúster.

Volver a proyectos

El problema

Cambios a mano, uno por uno

Cada instancia es un release de Helm. Para subir de versión, crear una instancia nueva o volver atrás, había que correr scripts desde un equipo, instancia por instancia. Era fácil equivocarse de destino o de versión, y después no quedaba registro claro de qué se había aplicado ni cuándo.

Cómo funciona

Producción a mano, desarrollo automático

En producción, una persona lanza el pipeline y lo aprueba. En desarrollo no hace falta: cada push a la rama develop lanza el pipeline solo, a través de GitHub Actions.

Lo que armé

Seis pipelines, uno por tarea

Todos se lanzan a mano desde Azure DevOps y, si no se cambia la opción, solo simulan.

Publicar imagen

Construye la imagen y la sube al registro. No toca ninguna instancia.

Actualizar catálogo

Lee qué instancias y versiones existen y actualiza las opciones de los formularios.

Actualizar una instancia

Cambia la versión de una instancia.

Actualizar varias

Hasta 10 instancias a la misma versión. Por defecto, de a una.

Rollback

Vuelve a la imagen anterior de hasta 10 instancias, una tras otra. Si una falla, se detiene.

Crear instancia

Revisa nombre, recursos y permisos antes de instalar. Si la instalación falla, Helm la revierte.

En la práctica

Cómo subo una versión a producción

  • 1. Publico la imagen si es una versión nueva.
  • 2. Actualizo el catálogo para que la versión aparezca en los formularios.
  • 3. Simulo: elijo las instancias y la versión, y reviso qué cambiaría.
  • 4. Aplico: lanzo otra corrida en modo aplicar. Espera la aprobación y, recién ahí, vuelve a revisar el estado actual del clúster y aplica.
  • 5. Reviso que la aplicación funcione en esas instancias antes de seguir con otras.

Controles

Qué evita errores

  • Listas cerradas: no se escribe el nombre de la instancia ni la versión; se eligen de una lista.
  • Aprobación con bloqueo: un cambio en producción necesita aprobación, y mientras uno corre no puede empezar otro.
  • Plan fresco: el plan se arma justo antes de aplicar, no se reutiliza el de una simulación anterior.
  • Accesos acotados: una identidad para publicar imágenes y otra para operar el clúster. El acceso al clúster es temporal, sin permisos de administrador, y se borra al terminar aunque el pipeline falle.
  • Registro: cada corrida guarda su plan y su resultado.
  • Límites de tiempo: 60 minutos por job, 15 minutos por actualización de Helm y 5 minutos por instancia en un rollback.

Un problema real

El rollback que no volvía atrás

Si las dos últimas revisiones de Helm tenían la misma imagen, el rollback elegía la anterior y no cambiaba nada. Lo corregí para que busque la primera revisión que tenga una imagen distinta, y agregué una prueba que falla con el código antiguo y pasa con el nuevo.

Otros problemas

Lo que también corregí

  • Rollback que decía "listo" sin hacer nada: si la versión de destino ya era la activa, el pipeline terminaba en verde. Ahora falla antes de tocar el clúster.
  • Diferencias entre Kubernetes y Helm: el rollback cambia la imagen directo en Kubernetes, así que Helm queda con otra versión registrada. Ahora no deja hacer otro rollback hasta corregir esa diferencia.
  • Error al crear una instancia: la validación previa esperaba un solo resultado y kubectl devolvía uno por recurso. Lo corregí; como falló antes de instalar, no quedó nada creado.

Desarrollo

El único despliegue automático

Para el ambiente de desarrollo hice un workflow de GitHub Actions. Con cada push a develop llama a Azure DevOps con ese commit, espera que el pipeline termine y queda en rojo si el pipeline falla. El token de acceso está guardado como secreto y no aparece en el log.

Lo que no cubre

Límites

  • Tengo pruebas para los scripts de los pipelines, pero los pipelines no prueban la aplicación ni buscan vulnerabilidades.
  • El bloqueo funciona para lo que pasa por los pipelines; un comando manual en consola no lo respeta.
  • El rollback devuelve la imagen anterior, no los datos. Tampoco se deshacen los datos que una instalación fallida alcanzó a escribir.
  • No publico código ni nombres porque son de la empresa.
