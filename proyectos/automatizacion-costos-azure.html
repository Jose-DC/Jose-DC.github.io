Caso de automatización cloud

Automatización horaria de recursos en Azure

Flujo programado para encender y detener un clúster AKS y PostgreSQL Flexible Server según una ventana de uso definida, reduciendo el tiempo que los recursos permanecen encendidos sin necesidad.

Abrir repositorio Volver a proyectos

Situación

Problema

AKS y PostgreSQL pueden seguir consumiendo recursos durante noches y fines de semana aunque un ambiente no productivo no esté siendo utilizado. El mismo patrón puede servir en producción cuando existe una ventana operativa aprobada.

Decisión

Qué se hizo

Se configuró Azure Automation fuera del clúster, con dos schedules e identidad administrada para ejecutar el orden correcto mediante permisos RBAC.

Estado real

Resultado

El ciclo manual se validó, la ejecución quedó habilitada de forma automática y se comprobó una reducción de costos. La cifra exacta se revisa por separado en Cost Management.

Diseño de la solución

La automatización vive fuera de AKS

Un clúster detenido no puede ejecutar su propio CronJob. Por eso Azure Automation controla el horario y coordina los recursos desde fuera del clúster.

Recorrido de la implementación

Cómo funciona el flujo

La solución se diseñó alrededor de las dependencias reales entre la base de datos, el clúster y sus workloads.

01

Programar la operación

Definir una ventana de trabajo

Se configuran dos schedules de lunes a viernes con la zona horaria de Santiago: uno para iniciar el ambiente por la mañana y otro para detenerlo al terminar la jornada.

Encender el ambiente

PostgreSQL antes que AKS

El runbook inicia PostgreSQL y espera a que Azure confirme el estado Ready. Solo después solicita el inicio de AKS y permite validar nodos, deployments y workloads.

Detener el ambiente

AKS antes que PostgreSQL

Al finalizar la jornada, primero se detiene AKS y se espera el estado detenido. Luego se detiene PostgreSQL, evitando que las aplicaciones queden funcionando contra una base de datos apagada.

Permisos y validación

Operar sin guardar claves

La cuenta de Automation usa una identidad administrada. Los permisos se asignan al alcance de los recursos necesarios y los schedules se habilitan después de probar el ciclo manual y comprobar la recuperación del ambiente.

Aprendizajes

Lo que me dejó este proyecto

  • Relacioné una decisión de infraestructura con un objetivo concreto de reducción de costos.
  • Practiqué dependencias de operación entre PostgreSQL, AKS y workloads.
  • Entendí por qué una automatización de encendido no debe depender del propio clúster.
  • Trabajé con identidad administrada, RBAC y separación de responsabilidades.
  • Aprendí a validar recuperación y schedules, no solo a ejecutar comandos de inicio o detención.
