Automatización horaria de recursos en Azure

Una guía resumida para coordinar el encendido y la detención de un clúster AKS y PostgreSQL Flexible Server según una ventana de uso, reduciendo costos cuando esos recursos no necesitan permanecer encendidos.

Abrir repositorio Volver a proyectos

Situación

Problema

AKS y PostgreSQL pueden seguir generando consumo durante la noche, los fines de semana o cualquier tramo fuera de la ventana de operación. Esto pesa especialmente en ambientes de prueba o no críticos, que no necesitan estar encendidos 24/7; en producción el mismo patrón puede aplicarse solo a workloads con horarios definidos y ventanas de mantención autorizadas.

Decisión

Qué se hizo

Se configuró Azure Automation fuera del clúster, con dos schedules, identidad administrada y permisos RBAC sobre los recursos que deben operarse.

Estado real

Resultado

El runbook se validó antes de activar la recurrencia y los schedules quedaron funcionando de forma automática. Una revisión preliminar de Cost Management mostró un gasto aproximado de USD 12 al día con los recursos encendidos, frente a USD 2,65 acumulados durante un fin de semana completo apagados — una señal de ahorro real, aunque falta repetir la medición por al menos dos semanas para fijar un porcentaje confiable.

Diseño de la solución

La automatización vive fuera de AKS

Un clúster detenido no puede ejecutar su propio CronJob. Azure Automation controla el horario y coordina el orden de los recursos desde fuera del clúster.

Implementación resumida

Qué se configuró

El runbook original contiene más pasos y comprobaciones. Aquí dejo solo los fragmentos importantes para entender la implementación sin convertir la página en un manual interminable.

01

Requisitos

Preparar el alcance de Azure

Se parte de un AKS y un PostgreSQL Flexible Server dentro de una suscripción autorizada. Antes de crear recursos se comprueban el contexto, los estados iniciales y el registro del proveedor de Azure Automation.

az account show --subscription "<SUBSCRIPTION>" --output table
az aks show --resource-group "<AKS_RESOURCE_GROUP>" --name "<AKS_NAME>"
az postgres flexible-server show --resource-group "<DB_RESOURCE_GROUP>" --name "<POSTGRES_SERVER>"
az provider show --namespace Microsoft.Automation --query registrationState
02

Automation e identidad

Crear el punto de ejecución

Se crea una Automation Account con identidad administrada. Esa identidad es la que ejecuta el runbook; la persona que configura los recursos y la identidad que opera el flujo pueden ser distintas.

az automation account create \
  --resource-group "<AUTOMATION_RESOURCE_GROUP>" \
  --name "<AUTOMATION_ACCOUNT>" \
  --location "<REGION>" --sku Basic

az rest --method patch \
  --url "<AUTOMATION_ACCOUNT_URL>" \
  --body '{"identity":{"type":"SystemAssigned"}}'
Connect-AzAccount -Identity -ErrorAction Stop
Set-AzContext -Subscription $SubscriptionName
03

Permisos y schedules

Autorizar y programar la operación

La identidad recibe permisos acotados a los recursos objetivo. Después se crea un schedule de inicio y otro de detención, ambos con recurrencia laboral y zona horaria de Santiago.

az role assignment list \
  --assignee-object-id "<AUTOMATION_PRINCIPAL_ID>" \
  --all --output table

# Schedules configurados en Azure Automation
START: lunes a viernes, 08:00, America/Santiago
STOP:  lunes a viernes, 23:59, America/Santiago
04

Validación automática

Comprobar que el horario funciona, incluso ante fallas transitorias

La prueba controlada se realizó antes de habilitar la recurrencia. El runbook es idempotente: revisa el estado real de cada recurso antes de actuar y reintenta con espera creciente si Azure no tiene capacidad disponible de inmediato. Al encender, valida además que los nodos y los despliegues queden disponibles dentro del propio clúster, no solo el estado reportado por el servicio administrado.

StartPostgreSQL Ready y AKS Running
StopAKS Stopped y PostgreSQL detenido
AutoSchedules con reintentos ante falta de capacidad
# Revisa el estado real antes de actuar: no repite una operación en curso
$state = (Get-AzPostgreSqlFlexibleServer -ResourceGroupName $ResourceGroup -Name $ServerName).State
if ($state -eq "Ready") { return }
if ($state -in @("Starting", "Updating")) {
    Start-Sleep -Seconds $PollSeconds
    continue
}

# Reintento con espera creciente si Azure no tiene capacidad disponible
$delaySeconds = [Math]::Min($MaxDelaySeconds, $BaseDelaySeconds * [Math]::Pow(2, $attempt))
Start-Sleep -Seconds $delaySeconds

Troubleshooting

Qué hacer si algo no calza

  • Proveedor no registrado: falta registrar el namespace de Azure Automation en la suscripción; se corrige registrándolo y validando el estado Registered.
  • Error de autorización RBAC: la identidad administrada no tiene permiso sobre ese recurso puntual; se revisa el alcance de la asignación, sin ampliarla a toda la suscripción.
  • PostgreSQL no llega a Ready: puede ser una operación en curso o falta de capacidad regional; no se reintenta el inicio mientras el estado siga en transición.
  • AKS no inicia: se revisa el Activity Log antes de reintentar, manteniendo PostgreSQL encendido mientras se diagnostica.

Aprendizajes

Lo que me dejó este proyecto

  • Relacioné una decisión de infraestructura con un objetivo concreto de reducción de costos.
  • Practiqué dependencias de operación entre PostgreSQL, AKS y workloads.
  • Entendí por qué una automatización de encendido no debe depender del propio clúster.
  • Trabajé con identidad administrada, RBAC y separación de responsabilidades.
  • Aprendí a validar recuperación y schedules, no solo a ejecutar comandos.
  • Un primer encendido automático falló por un problema transitorio al cargar módulos de PowerShell; lo resolví agregando una validación explícita de dependencias y un reintento completo del flujo antes de declarar error.
